# project-doc-system v2 文本行为审查

Owner: Sean  
日期：2026-10-14  
对象：更新后的 SKILL、maintenance/design-and-tools references、四份 assets。仅模拟文本行为，没有执行场景或调用任务系统。

## 场景一：只改操作手册一个参数，已有 Task Center 与 ledger

预期：沿入口定位手册和参数权威位置，读相关证据与涉及文件工作树；如果手册只是消费参数，改其指针或真实权威正文；若手册拥有参数则直接修改。用户授权参数调整且已有依据时复用依据，不制造新实验。只有结论发生变化时按既有 ledger 协议追加；更新受影响直接引用，任务生命周期沿项目协议处理。无需全库审计、新 ADR 或另建索引。

潜在过度工作：主文件写入顺序第 2 步「先落可核对的证据」容易被读成每次改一个值都新建证据文件，第 4 步又像要求每次编辑都创建新旧记录。建议加一句：已有证据足够时直接引用；纯纠错或不改变结论的编辑无需新增证据/替代记录。若新值只是用户决定、无验证材料，应记录采用来源与未验证边界，不为补证据擅自运行实验。

## 场景二：依赖库升级，只重排章节

预期：按直接引用找到相关研究项，临时标待复核；核对旧新版本所依赖段落是否语义相同，修新章节定位或保留旧固定快照作为当时证据。确认语义与适用范围不变后，记实际查验版本及结论，解除待复核；不标已失效、不改原实验结果、不重跑实验。maintenance 已明确无关格式变化无需重跑，指导充分。

潜在错误：把「更新检查条件/查验版本」执行成覆盖旧实验的运行版本。主文件保留历史环境的条款能抵消此误读，仍可在 maintenance 加一句：当前适用性复核单独记录，本轮查验版本不替换原证据的观察版本。

## 场景三：新项目有自研 .pi/skills、少量产品 PNG、大批生成 MP4

预期：先确认项目现有治理和文件用途，建立小型入口与需要的权威页；在项目范围初始化 Git 或复用已有仓库。自研 .pi/skills 和必要产品 PNG 可入库；大量生成 MP4 通常仓库外保存，入库 manifest/恢复索引。按实际路径补忽略规则，避免整目录排除 .pi/ 或按图片扩展名一刀切。不自动公开、上传媒体或构建站点。

潜在遗漏：gitignore 中批量产物排除只有注释示例，若机械复制后立即提交，MP4 仍可能进 Git。文件已经要求按项目修改，因此不是模板错误；建议新项目起步的动作里明确「提交前检查待跟踪路径是否含批量产物」。没有必要建立统一 PNG 白名单。

## 仍需注意

- **文件规则与表格例子有轻微张力**：主文件允许操作手册作为步骤/参数真源；maintenance 的映射表把「操作页旧参数表」直接处理为指针。例子应注明「同一参数已有独立 reference 真源时」，避免普遍删除执行所需参数。
- **必做替代关系范围过宽**：写入顺序第 4 步建议限定为「发生结论取代或迁移时」。一般章节重排、拼写修正和参数抄错纠正不必新建后继记录。
- **模板不是机器协议**：assets 均为可人工填充 Markdown，没有 YAML 或解析器承诺。`<…链接>` 是占位文字，若原样复制会被 HTML 渲染隐藏；应填入真实 Markdown 链接并删除不用行。可将注释补为「交付前替换全部占位符」，无需引入解析工具。
- **没有发现新旧真源严重矛盾**：Task Center、当前技术正文、ledger、历史快照分工清楚；决定采用、证据有效性与任务验收已明确区分。没有要求全库哈希、四类目录、安装工具或默认补测试。

优先补第一项场景中的「复用已有证据、仅实质替代才留替代记录」，其余可以轻量澄清，不应再扩展主文件流程。
