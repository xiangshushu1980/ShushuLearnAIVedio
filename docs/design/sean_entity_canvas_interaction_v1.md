# 实体画布实验：项目结构、交互与数据契约 v0.1

> Owner: Sean。2026-10-07。用户已确认实验路径与规模；本文是该路径的详细设计草案，不代表施工已批准。总体架构见 [实体画布设计](sean_entity_canvas_pi_v1.md)。

## 1. 已确认的实验

一个项目、两章、每章一个剧情场景。临时小说后续编写，专为验证共享上下文、关系和局部状态，不以文学完成度为目标。

固定验收路径：导入小说 → PI 分析两个人物、一个地点、一件道具及关系 → 人工采用 → 跨章讨论并记录局部状态 → 为一个人物生成图片 → 选图反馈再生成 → 人工确认 → 刷新恢复。

首期不做剧本编辑、拍摄本或视频生成；章节和剧情场景只负责上下文归属、状态及来源引用。样本内容不是生产设定，不沿用旧实验中的人物或剧情冒充本次小说。

## 2. 项目组织与上下文

```text
项目
├── 项目设定：简介、世界规则、时代、视觉风格、已采用决定
├── 原始资料：小说修订、段落锚点、笔记
├── 实体：人物 A、人物 B、地点 L、道具 P
├── 讨论：原文分析、关系设计、人物外观、第二章局部状态
└── 章节
    ├── 第一章：目标/梗概 → 场景 1 → 实体引用、状态
    └── 第二章：目标/梗概 → 场景 2 → 实体引用、状态
```

地点 L 是可复用实体；Scene 是某章的一次剧情事件。两个 Scene 可引用同一地点，不能因复用地点而合并剧情场景。界面使用“地点实体”和“剧情场景”明确区分。

项目规则是共同基准；章节说明补充本章意图；场景保存当次发生条件。下层不能静默覆盖上层规则：冲突进入提案，由用户决定修改共同设定还是登记有明确范围的例外。对象归属由 ID 与父级约束决定，不靠标题和文件目录猜测。

实体拥有全项目稳定身份和设定版本。剧情场景通过 EntityUse 引用具体实体版本，保存本场角色、服装/身体状态、持有道具及来源。只有持续且需要独立视觉资料的状态才升级为变体；一次状态变化不自动创建新实体。

本期项目设定用少量字段即可；章节和场景支持新建、命名、简要说明及引用资料。无需在开始创作前填完表，也不要求每段讨论先归入章节。没有归属的讨论可留在项目层，之后显式链接。

## 3. 画布与导航

固定界面：左侧项目树和对象索引，中央自动布局画布，右侧当前讨论与上下文，顶部显示当前聚焦范围和定位入口。

| 聚焦视图 | 中央呈现 | 主要操作 |
|---|---|---|
| 项目总览 | 共同设定、资料、章节摘要、实体摘要和待决定事项 | 打开讨论、定位对象或章节 |
| 资料分析 | 原文片段、分析讨论、实体/关系候选 | 核对来源、修订与采用 |
| 实体设计 | 设定、参考图、生成输入、运行、结果版本 | 讨论、调参、生图、比较与确认 |
| 章节/剧情场景 | 目标、剧情简述、出场实体和本场状态 | 引入资料、多对象讨论、采用局部状态 |

这些是同一项目数据的投影。切换视图不复制实体、不创建新 PI 会话、不调用模型。返回视图恢复其视口与折叠状态；跨对象引用提供定位按钮。

卡片单击选择并展开摘要；多选可使用复选框或组合选择。点击“加入本轮讨论”才进入上下文托盘，托盘显示角色：目标、依据、对照。点击引用定位与加入讨论是不同操作。

同一实体在不同视图的卡片均指向 entityId；位置 ID 可不同，业务事实只有一份。线条用文字/图标标明“依据”“关系”“使用”“生成自”，不单靠颜色。关系线不代表生成依赖。

首期不提供拖拽节点、连线、流程图编辑或自由空间编排。长原文、参数、旧运行和实体细节默认折叠，用户展开查看。

## 4. 验收流程逐步交互

| 步骤 | 用户动作 | PI / 服务行为 | 可见结果 |
|---|---|---|---|
| 1 项目与原文 | 新建实验项目，录入/导入短文本，建立两章两场归属 | 保存不可变原文版本及段落锚点 | 项目树、资料卡与结构卡 |
| 2 初次分析 | 选原文与项目规则，发起实体分析 | PI 按需读片段，提出四个实体及关系候选 | 候选卡有依据、未知和保存目标 |
| 3 采用 | 检查/编辑候选，点击采用所选项 | 事务建立实体、关系及采用记录；不生成图片 | 正式实体 ID、关系、讨论回链 |
| 4 跨章讨论 | 选第二章场景、人物及道具，讨论本场变化 | 提案明确 scope=scene；不改人物全局设定 | 新旧差异与“仅第二章本场”标签 |
| 5 局部状态采用 | 点击采用局部状态 | 保存 EntityUse 版本；第一章引用不变 | 两场人物状态可对照 |
| 6 人物图片 | 聚焦人物，讨论目标并查看 Qwen 输入草案 | 生成参数、引用顺序、模板与有效提示词预览 | 输入卡和“生成这一版”动作 |
| 7 执行 | 明确执行单次生成 | 建立动作快照与 run；PI 返回 runId，执行器继续运行 | 真实状态、结果组、来源 |
| 8 反馈 | 选候选与原输入，要求修改 | PI 查看必要图片，提出新输入，显示实际差异 | 新输入版本，不覆盖旧 run |
| 9 再生成 | 明确执行第二轮 | 固定新输入并建立新 run | 两轮可并排比较 |
| 10 确认与恢复 | 点击设为主形象，再刷新/重开讨论 | 保存人工确认并重读业务对象 | 当前确认、历史、来源与局部状态一致 |

采用部分候选时检查依赖：若关系端点仍是未采用候选，不能保存悬空正式关系；可一并采用端点，或留为候选。服务不能因用户采用人物而偷偷采用所有关系。

实验中第二轮只调整一个可辨识目标，例如背景或一项服装细节。具体目标在小说和首图明确后确定，不预先承诺模型一定实现。验收既核对实际输入变化，也记录实际视觉结果。

## 5. PI 动作边界与执行交互

讨论、提案、采用和执行是四种动作。首期可靠基线为：对话可自由讨论及保存候选；采用、生成和确认由对应对象上的明确动作触发。自然语言快捷执行可后续加入，但不能成为首期闭环成立的前提。

| 动作 | PI 权限 | 生效方式 |
|---|---|---|
| 阅读与讨论 | 读取项目内有权限的资料，实际看图有记录 | 不改设定 |
| 保存提案 | 保存结构化候选、依据、目标和差异 | 自动保存候选，不成为现行事实 |
| 采用设定/关系/局部状态 | 可解释和建议 | 人工动作触发服务事务 |
| 生图输入修订 | 提出新输入、编译并预览 | 草案与正式采用设定分开 |
| 启动图片生成 | 工具可执行服务签发的单次动作 | “生成这一版”固定实体、输入 hash 和预算一次 |
| 主形象确认 | 可建议 | 用户点击设为主形象 |

用户说“继续”时，PI 根据当前讨论说明下一步或保存提案，不能跨过尚未采用的设定或把它解读成无限生图授权。授权对象和实际输入版本必须一致；修改后旧授权不再可用。重复点击返回原动作/run。

多实体讨论不等于多实体写权限。提案列出每个目标及 scope；采用时原子校验所有受影响版本。一个项目首期一次一个 PI 执行轮次，异步生图可继续显示，讨论新结果前可查看真实执行状态。

## 6. 最小数据契约

名称是领域契约，表结构可在施工设计中映射；不要求创建同数量的数据库表。

| 对象 | 必要字段/约束 |
|---|---|
| Project | id、owner、名称、共同设定、revision |
| Chapter | id、projectId、顺序、名称、目标/梗概、revision |
| Scene | id、chapterId、名称、剧情简述、地点引用、revision；project 由 chapter 确定 |
| SourceDocument / Anchor | projectId、sourceId、不可变 sourceRevision、原文、paragraphId/范围/hash |
| Entity / Revision | projectId、entityId、类型、名称、设定及不可变修订 |
| Relation | projectId、端点、类型/说明、scope、来源及 revision；初期端点为实体 |
| EntityUse | sceneId、entityId、entityRevision、状态、用途、道具引用及来源；道具也有实体身份 |
| Discussion | projectId、目标、链接对象集合、PI 会话绑定；可无章/场归属 |
| Proposal / Decision | 涉及对象、scope、基准版本、字段差异、依据、采用/拒绝记录 |
| ImageInput / Run / Asset | 固定实体与可空 EntityUse 版本、提示词、引用顺序、参数、模板 hash、实际 run 和候选 |

稳定编号与 revision 分开；正式实体不使用候选 key。章节/场景归属和引用必须同项目。实体引用默认固定版本，不因全局修改悄悄更新历史场景；界面提示可更新，用户显式采用。

小说提取的事实标记原文依据；用户新增设计标记决定依据；PI 推断保留候选/未知标记。缺少服装等信息可以提出设计建议，不能冒称小说已写明。

人物基准形象使用全局实体设定。本场带伤/换装图使用 EntityUse 或明确变体，确认时标为本场用途；不能用局部状态图静默替换全项目主形象。此次两轮生图默认验证基准形象。

## 7. PI 本轮上下文与恢复

每轮 ContextSet = 项目共同基准 + 当前讨论目标 + 明确选中的对象/原文片段 + 当前章/场必要说明 + 已采用相关决定。展开卡片不自动读给模型，引用对象过多时先给索引，工具按需读取并记录。

选第二章场景时可以引入第一章的已采用人物/道具状态作对照，不能把第一章整段对话默认作为当前事实。界面提供“本轮带入”“实际读取”“历史会话仍含内容”三类说明；从上下文移除不会抹掉 PI 历史。

恢复按业务资料重建摘要，不把聊天总结当现行设定。重新进入显示：当前目标、待采用提案、进行中 run、待用户决定事项和最近采用记录。PI 不自动续发计费请求。

数据变化与事件同事务持久化；画布按 seq/revision 幂等更新。提交未知先查询原 action/run，不自动创建重试。取消 PI 与取消生成是两个操作。

## 8. 工程组织草案与宿主决策

工程层需要独立于产品内项目：开发仓库保存代码、skill 注册和设计；产品数据目录保存创作项目、原文、媒体及运行。产品项目不是开发 repo，也不是 Codex 的 Task Center 任务。

```text
应用代码
├── project-domain/       项目、章节、场景、设定、来源和采用
├── discussion/           讨论、上下文、PI 会话和受限工具
├── canvas/               对象投影、布局、选择和详情
├── execution-adapters/   固定 Qwen 输入与运行接口
└── data/                 应用私有库、media、恢复信息（不提交 Git）
```

这是逻辑模块，不是已决定新建这些目录。采用新应用还是现有宿主仍需比较：既有 PI 工具是否依赖旧会话归属、生成模块能否独立调用、数据如何确定唯一真源、原服务是否可隔离验证。本文不把复用成本未经核实地写成已解决。

本期不将每个章节、场景和实体建成远程任务。应用库负责实时业务推进；设计确认后创建的 Task Center 施工任务只管理开发工作。未来若接入产品制作任务，映射项目与目标，不以任务列表替代作品结构。

## 9. 设计验收与尚待冻结

本设计覆盖用户确认路径。施工前还需冻结：应用宿主与服务边界、PI 部署与认证方式、画布组件、物理 schema/API、实验小说及明确的画面修改目标。可由 Codex继续分析形成具体方案，再一次审阅，不逐个技术细节重复请用户批准。

验收记录应分别给出：

- 跨章节上下文与局部状态是否正确；第一章及全局设定有无误改。
- 多对象讨论、提案来源和人工采用是否可追溯。
- PI 是否调用真实受限工具；两轮 Qwen 是否使用实际已展示输入。
- 图片是否达到用户目标；执行成功与图像效果分别判定。
- 刷新与中断恢复是否重复执行、丢失采用或串到其他对象。

当前仅文档设计，未写应用代码、运行模型或提交生成，未创建/启动施工任务。
