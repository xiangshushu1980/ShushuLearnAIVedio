# Seedance Director 4.0：实体、创作讨论与画布架构参考

> Owner: Sean。调研日期：2026-10-07。用于实体无限画布与 PI 的分析设计，不安装外部 skill、不执行其工作流、不创建施工任务。
> 仓库快照：`86cf3cb1c42429d79be6b6373caf18a411135254`，默认分支 master；该提交日期 2026-09-13。视频发布日期 2026-09-17，18 分 48 秒。以下区分公开材料、可见演示与本项目设计推论。

## 1. 核心判断

最值得借鉴的是创作资料与产物之间的组织契约：原始文本、项目创作意图、实体资料、下游引用、确认决定和连续性分别管理。聊天窗口可更换，业务依据不依附于某个窗口。

因此我们的讨论模型应支持多份资料和多实体，并让选定结论分别进入实体、关系或剧本引用。具体生成仍绑定单个目标及固定输入版本。画布负责显示这些对象和来源关系，固定工作流负责执行。

公开仓库主要是技能和模板，不能据此认定提供了可复用的画布应用或 Agent/画布同步实现。其终点是提示词工程文件，图片与视频生成交给用户；我们要补足 PI 调用执行器、运行状态和结果回流。

来源：[项目说明](https://github.com/aaronbedolla560-cell/Seedance-Director-4.0/tree/86cf3cb1c42429d79be6b6373caf18a411135254)、[主控规范](https://github.com/aaronbedolla560-cell/Seedance-Director-4.0/blob/86cf3cb1c42429d79be6b6373caf18a411135254/CLAUDE.md)。

## 2. 原项目如何划分工作

### 原始资料与创作决定

`shougao` 将想法、小说、剧本等分型，并保存原文修订；改编和产物另存。`bianda` 的蓝图定义意图、范围与风格，并区分假设和待决定事项。项目决定保存在独立记录中。

可借鉴：原文是证据，创作方案是解释，用户采用是决定。三者应分别有版本和来源，讨论内容不能直接变成原文事实。

来源：[收稿契约](https://github.com/aaronbedolla560-cell/Seedance-Director-4.0/blob/86cf3cb1c42429d79be6b6373caf18a411135254/.claude/skills/shougao/SKILL.md)、[蓝图模板](https://github.com/aaronbedolla560-cell/Seedance-Director-4.0/blob/86cf3cb1c42429d79be6b6373caf18a411135254/.claude/skills/bianda/templates/lantu.md)。

### 实体及其视觉资料

资产按角色、场景和道具组织，使用稳定项目编号。完整描述、简短身份引用和生成图侧指令各有用途；持续外观变化登记变体并保留父版本。场景有共享几何依据，道具包含可辨识状态。

本项目应借鉴稳定身份、变体来源和按用途组织资料。角色/场景/道具可作初始分类，但不能将整套实体数据固化成三份提示词文档。

来源：[资产技能](https://github.com/aaronbedolla560-cell/Seedance-Director-4.0/blob/86cf3cb1c42429d79be6b6373caf18a411135254/.claude/skills/zichan/SKILL.md)、[角色描述层次](https://github.com/aaronbedolla560-cell/Seedance-Director-4.0/blob/86cf3cb1c42429d79be6b6373caf18a411135254/.claude/skills/zichan/references/juese.md)、[状态与变体](https://github.com/aaronbedolla560-cell/Seedance-Director-4.0/blob/86cf3cb1c42429d79be6b6373caf18a411135254/.claude/skills/zichan/references/shengxian-bianti.md)。

### 下游引用与方法加载

项目资产编号与某次生成中的上传序号分开，编译时显式映射，每份参考声明用途。技能入口只给方法索引，需要时读取具体 reference/template/example。

可借鉴：entityId/assetId 是稳定身份，Image1 等是本次输入位置；讨论中的相关图片不自动成为生图输入。PI 按操作加载方法，避免全量装入制作规则。

来源：[参考绑定规则](https://github.com/aaronbedolla560-cell/Seedance-Director-4.0/blob/86cf3cb1c42429d79be6b6373caf18a411135254/.claude/skills/bianyi/references/bangding.md)、[操作指南](https://github.com/aaronbedolla560-cell/Seedance-Director-4.0/blob/86cf3cb1c42429d79be6b6373caf18a411135254/操作指南.md)。

### 进度、审核和恢复

进度通过项目产物、确认记录和连续性资料恢复；审核与创作职责分开。变更上游后提示受影响下游，不能静默改写已确认内容。

可借鉴恢复与事实分离。我们的后台应有显式状态和事件，不使用文件存在或 mtime 判断任务已经完成；检查报告作为建议，用户采用仍独立。

来源：[主控状态路由](https://github.com/aaronbedolla560-cell/Seedance-Director-4.0/blob/86cf3cb1c42429d79be6b6373caf18a411135254/CLAUDE.md)、[连续性技能](https://github.com/aaronbedolla560-cell/Seedance-Director-4.0/blob/86cf3cb1c42429d79be6b6373caf18a411135254/.claude/skills/lianxu/SKILL.md)。

## 4. 对本项目的关键设计修正

### 4.1 讨论是独立对象

“一个实体一个对话”与“全项目共用一个对话”都不应成为数据约束。可以从小说片段开始分析两个人物，也可以围绕一件服装单独讨论，或从闲聊沉淀出尚未命名的实体。

Discussion 与 SourceDocument、Entity、Relation、图片及步骤是多对多。用户可以继续已有讨论或新开讨论；选中对象控制本轮上下文，固定资料作为可见的 pinned context。

取消选择只代表下一轮不主动注入，旧 PI 历史仍可能包含内容。要求真正隔离时建立新 PI 会话，转入明确选择的资料和已采用决定，不承诺模型遗忘历史。

### 4.2 分清分析、事实、设计和执行

| 层 | 示例 | 是否直接生效 |
|---|---|---|
| 原始资料 | 小说某段、剧本片段、用户消息 | 保存原文或消息引用 |
| 分析提案 | 推断两人是师徒、建议用相近服装表达关系 | 候选，需标明依据与不确定 |
| 已采用设定 | 用户接受两人为师徒，角色 A 的确定外观 | 写入实体/关系对应版本 |
| 生成输入 | 本轮提示词、图片职责、顺序和参数 | 显式执行时固定快照 |
| 图片与确认 | 候选图、用户选定主形象 | 生成成功不等于确认 |

关系是可引用的业务对象，有端点、类型、说明、来源和适用范围。人物固有关系与某个故事阶段的关系可用 scope 区分，不把“本场伪装成敌人”变成永久实体事实。

### 4.3 实体与图像资产分开

Entity 管稳定身份；EntityRevision 管设定版本；EntityVariant 管换装/受伤等设计状态；Asset 管图片字节及来源；GenerationRun 管一次执行。重试产生新 run，不自动成为新实体或变体；改文字也不必产生变体。

首期只需要基础实体、修订与图片，变体可保留类型契约后再完整实现。第三方的角色三格、去头、纯正向和平台输入上限属于其制作方法，不直接作为 Qwen Image 2.1 的硬规则。

### 4.4 与未来剧本部分通过版本引用相接

SourceAnchor 定位原文版本与段落/字符范围；Decision 记录采用结论；StoryLink 连接实体版本、关系版本与剧本引用位置。来源原文变化后标记待重新定位，不静默把旧引用移到另一段。

实体改动时列出受影响的剧本引用，用户在未来剧本工作区决定采用更新。首期只实现文本资料和引用记录，不施工剧本编辑、镜头或视频流程。

### 4.5 画布呈现工作对象和真实来源

建议分为“资料与讨论 / 实体与关系 / 图片输入与结果”三个可聚焦区域，自动布局。线型分别表达来源、语义关系、生成依赖；卡片邻近不自动构成依赖。跨区域引用可点击跳转，无须始终展开所有长文本。

用户可以同时选两个人物和一段原文请求分析关系；最终的生图动作仍明确目标实体，图片引用单独列明。新增对象可按讨论来源成组，并保留位置稳定，避免每次回复全图跳动。

## 5. 现有系统是否复用

当前应先冻结业务契约和交互，不把旧页面或旧数据库设为必须兼容的内核。评估三个选项：

| 选项 | 好处 | 代价与适用条件 |
|---|---|---|
| 在 Reference 内加画布 | 接入现有 PI、素材与 Qwen 服务较直接 | 需要扩展原会话归属，容易被旧页面编排限制 |
| 新建应用，适配既有能力 | 画布、讨论和上下文可按新模型组织 | 要明确生成/资产服务的边界及唯一数据真源 |
| 连生成后端也重建 | 边界完全重新设计 | 扩大范围，必须有旧服务无法适配的具体证据 |

当前设计倾向先验证前两项；允许独立应用，优先复用经过验证的固定工作流、输入契约、幂等与产物回收经验。选择依据是能否低成本支持本期交互，不以“已经写过很多代码”作为决定理由。

## 6. 本期应实现的最小验证

1. 粘贴一段小说/剧本或从闲聊开始，创建讨论，不强制先建实体或远程任务。
2. PI 提出两个实体及一条关系，显示原文依据和未知；用户分别审阅采用。
3. 选中两实体及原文继续讨论；新开另一讨论也可引用同一实体，修改使用版本检查。
4. 聚焦其中一个实体，使用固定 Qwen Image 2.1 做一轮生成；结果回原区域。
5. 选中候选反馈，展示实际有效输入差异，明确执行第二轮，用户比较并选择主形象。
6. 刷新恢复来源、讨论、实体/关系和运行；保存未来剧本引用所需信息，暂不运行视频流程。

第一期不承诺整部小说自动抽取、复杂关系图、多个 PI 并行改写、跨项目自动共享或自动多轮修图。多对象讨论属于核心验证，不应因“只做单实体生成”被删掉。
