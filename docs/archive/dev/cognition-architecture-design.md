# 认知架构设计：统一记忆系统的分层 + ID 互通（待 codex 复查）

> 状态：设计草案（v1），待 codex 复查与用户拍板
> 背景：用户想把散落的记忆/知识系统统摄成一个有层级的认知架构，核心诉求是
> ①数据分开但 ID 互通 ②能升到用户级 ③避免膨胀。

---

## 〇、现状盘点（实测）

用户当前有 4 套记忆/知识系统，它们不是同层的东西：

| 系统 | 位置 | 存什么 | 主角 | 可变性 | 当前层级 |
|---|---|---|---|---|---|
| **ledger** 结论谱系 | `comfy-ops/.pi/ledger/`（项目级） | 定论/结论的演进史、覆盖链、证据锚（28 条 C-ID） | 结论 C-ID | **不可变**（append-only） | 项目级 |
| **mem0** 共享记忆 | MCP 服务（global + 项目池） | 经验/踩坑/偏好（检索式） | 经验片段 | 可变可删 | 已是用户级 |
| **mentor** 导师概念 | `~/.pi/agent/mentor/concepts.json` | 概念掌握度/熟练档 L0-L3/复习计划 | **用户本人** | **可变**（升档/复习） | 已是用户级 |
| **TODO** 任务 | `~/.pi/agent/todo/` | 任务待办（T-ID，四态机） | 任务 T-ID | 可变 | 已是用户级 |

**核心矛盾**：ledger 的主角是"结论"（不可变），mentor 的主角是"用户本人"（时刻变）。
因此物理合并会毁掉 ledger 的 append-only 本质——这是设计必须避免的。

---

## 一、设计原则：认知分层 + ID 互通（不物理合并）

**不把所有系统物理搬进一个文件，而是在用户级建一个"认知层"，通过统一 K-ID 引用所有知识源。**

- 数据分开：每个系统保留自己的内部结构、职责、可变性
- ID 互通：跨系统用统一知识对象 ID（K-ID）作锚点，互不持有对方内部字段
- 最小耦合：任一系统改内部结构不影响其他（mentor 是"去取"本体，不是"被推送"）

---

## 二、分层模型（一源多态）

```
┌──────────────────────────────────────────────┐
│ 认知状态层（mentor）——主角是你，唯一可变层     │
│   概念掌握度/熟练档 L0-L3/复习计划/误区记录     │
│   数据：concepts.json（不持有知识本体，只引用） │
└──────────────▲───────────────┬───────────────┘
        按 K-ID 引用（取本体）    按 K-ID 回写（验证掌握）
         │                       │
┌────────┴───────────────────────┴──────────────┐
│          统一知识对象 ID：K-ID                  │
│    （跨系统唯一锚点，如 K-h3-vae-nvfp4）         │
└──────────────▲────────────────┬───────────────┘
   ┌───────────┴────┐     ┌─────┴─────────┐
   │ 知识本体层       │     │ 经验层         │
   │ ledger 定论     │     │ mem0 经验      │
   │ docs 现行手册   │     │ global+项目池  │
   │ skills 操作     │     │               │
   └────────────────┘     └───────────────┘
         ↑ 来源可追溯            ↑ 检索式
   ┌───────────────────────────────────────────┐
   │ 证据/行为层：TODO T-ID + progress + git     │
   └───────────────────────────────────────────┘
```

## 三、ID 互通接口设计（最小耦合）

**原则：只引用 K-ID，不复制本体，不持有对方内部字段。**

一个知识对象 K-ID 在各层的表示：

| 系统 | 怎么引用 | 示例 |
|---|---|---|
| **ledger** | 条目头加 `K-ID:` + `来源:` 字段 | `K-ID: K-h3-vae` / `来源: mem0 521b2a49 / docs 02 §VAE / T-comfy-ops-XX` |
| **mentor** | 概念条加 `sources:` 数组 | `sources: [{kind: ledger, id: K-h3-vae}, {kind: docs, id: 02}]` |
| **mem0** | 经验正文带 K-ID 标签 | `[K-h3-vae] 视频 VAE 8x 下采样……` |
| **TODO** | 任务关联知识对象（可选） | 可选的 `K:` 字段 |

**价值**：mentor 复查某概念时，沿 `sources` 知道去哪取本体（ledger 现行值 / docs 细节 / mem0 的坑），
但 mentor 自己只管"你熟不熟"。ledger 修订时无需通知 mentor（去取而非被推送）。

---

## 四、mentor 记录什么 + 知识来源（5 类入口）

**mentor 记录的是"你对一个知识对象的掌握状态"，不是知识本身。**

```json
{
  "concept": "H3 VAE 选型",
  "k_id": "K-h3-vae",
  "domain": "comfyui",
  "level": 2,
  "streak": 3,
  "next_review": "2026-08-24",
  "sources": [
    {"kind": "ledger", "id": "K-h3-vae", "status": "现行"},
    {"kind": "docs", "id": "02_models"},
    {"kind": "mem0", "id": "521b2a49", "note": "VAE 8x 下采样丢微细节"}
  ],
  "know_unknown": "知道用哪个、不知为何",
  "misconceptions": ["以为 nvfp4 用不了，实际是模拟跑"]
}
```

**"ledger 只是 mentor 的一个入口"——正确，且不止一个。** mentor 的 `sources` 支持 5 类：

| 来源 kind | 从哪来 | 特点 | 存不存本体 |
|---|---|---|---|
| `ledger` 定论 | 结论谱系（升用户级后跨项目） | 权威、可演进 | 否，引 K-ID |
| `docs` 现行手册 | 项目文档 | 细节/参数表 | 否，引章节 |
| `mem0` 经验 | 共享记忆池 | 踩坑/偏好、检索式 | 否，引 id |
| `network` 网络查询 | 临时查到的 | 易失效 | 存 URL + 一句话摘要 |
| `world` 世界知识/常识 | 模型训练知识 | 不进库 | 标注"常识，无来源" |

## 五、落地路径（三小步）

1. **试点**：本项目 3 条关键定论升级为统一 K-ID（`K-h3-vae` / `K-h3-nvfp4` / `K-h3-hybrid`），
   在 ledger 和 concepts.json 两边加引用，跑通"聊定论 → mentor 记掌握 + ledger 记演进"闭环。
2. **ledger 升用户级**：用户级建 `~/.pi/agent/ledger/` 作统一索引（K-ID 映射 + 核心定论摘要），
   各项目详细正文保留在项目文件。避免全局文件膨胀。
3. **mentor 补来源链**：`sources` 字段规范化，支持 5 类 kind。

## 六、待拍板 / 待复查问题

1. **K-ID 命名**：按主题域（`K-h3-*`）还是按系统（`K-ledger-*`）？倾向主题域，跨系统统一。
2. **ledger 升用户级的边界**：正文留项目、只上移索引？还是核心定论全上移？
3. **上下文优化**：如何避免全局文件/索引膨胀导致 agent 每次会话检索成本上升？
   是否引入 K-ID 注册表（轻量，仅映射）+ 正文惰性加载？
4. **mem0 的双重角色**：mem0 既是经验层又被 ledger 引用为"证据锚"，是否需要在 mem0 里也登记 K-ID 索引？
5. **网络/世界知识的时效**：`network` 来源易失效，是否设过期机制（TTL）？
