# H3 数字人技术推论

本文件是基于官方资料、开源代码和社区观察形成的推论，不是官方声明。

## 1. 本研究的目标定位

本研究不把镜头调度作为必要条件。核心问题是：在固定或低调度的主持人场景中，H3 能否凭借参考图细节、latent 放大、MC 连续续接和正式全精度分片，获得比 InfiniteTalk 更好的脸部细节、身份保持和整体成片质量。

H3 仍更适合作为“镜头级数字人导演模型”，而不是传统固定头像口型模型；但本项目的第一验收目标是连续数字人和成片质量，而不是复杂镜头。

InfiniteTalk 更像“音频主导的长时人物动画系统”。因此 H3 的质量上限更高，但长时主持人输出需要额外工程层。

## 2. 文稿和音频的分工

如果将完整文稿直接交给 H3，模型需要同时解决台词、语音、口型、表情、身体、机位、身份和长时间状态传递，这些目标会竞争。

更合理的分工是：

```text
最终播音音频 → 时间主线
文稿         → 语义与镜头意图
H3           → 视觉表演、动作、镜头和环境
```

本轮已有成对测试输入：一份确定的粤语播音音频，以及与其逐字对应的口播稿。测试时必须固定使用这对输入：音频不重新 TTS，稿件不作为 H3 重新配音指令；稿件用于确认音频内容、标记语义段落、停顿和潜在镜头边界。所有 H3、InfiniteTalk 和后续方案必须使用同一音频，才能比较口型、连续性和画质。

## 3. InfiniteTalk 机制可迁移的部分

可迁移的不是 Wan 权重，而是四个思想：

1. 音频是主时间条件；
2. 身份和机位通过稀疏参考帧锁定；
3. 上一块尾部 context 传递运动惯性；
4. 每个 chunk 生成后把状态交给下一块。

H3 社区的 Motion Context、LongMedia、Continuum 和 latent chaining，本质上是在尝试将这四个思想放到 H3 的 video/audio latent 上。

## 4. 连续画面的四种连续

主持人长视频真正需要保持的是：

```text
音频连续 → 台词、停顿和重音不变
身份连续 → 脸、发型、服装、体态不漂移
动作连续 → 上一段的运动趋势延续
镜头连续 → 景别、机位和屏幕空间逻辑连续
```

这四种连续可以由不同机制共同完成：音频时间轴、角色参考图、latent/context、首尾帧和剪辑。

## 5. 角色参考图推论

角色参考图应视为“角色模型输入”，而不是普通素材。单一头像不足以覆盖正脸、三分之四脸、侧脸、半身、全身、面向大屏和坐姿到站姿。

建议参考资料覆盖角度、景别、服装、表情和姿态；但参考图不是越多越好，服装、光线、年龄和脸部特征互相冲突时可能降低一致性。

## 6. 主持人动作风险分层

| 动作 | 适配度推论 | 原因 |
|---|---:|---|
| 正面播音、眨眼、点头 | 高 | 身体状态简单，脸部条件稳定 |
| 小幅推镜、三分之四转头 | 高 | H3 的镜头和姿态变化优势明显 |
| 半身轻微手势 | 中高 | 有表现力，但手部开始成为风险源 |
| 起身、转身、走向大屏 | 中 | H3 有能力，但应拆成动作镜头 |
| 边走边说、指屏幕 | 中低 | 身体、手、口型、屏幕和身份同时竞争 |
| 多人互看和交叉遮挡 | 低到中 | 多身份、音频归属和遮挡共同增加难度 |

起身走向大屏可能是 H3 相比 InfiniteTalk 的优势，但不应作为第一阶段的口型基线。

## 7. 长时方案推论

最可能稳定的架构不是“无限生成一个 latent”，而是：

```text
完整粤语 TTS 母带
→ 语义时间轴
→ MC 驱动的短片段视觉生成
→ video/audio context 继承
→ 高细节角色参考图重申
→ latent 放大或全精度分片
→ 必要时首尾帧锚定
→ 局部脸部精修
→ 接缝和身份检查
```

长片连续感来自音频、身份、动作和镜头的共同连续，而不是必须一次采样完成。

## 8. H3 和 InfiniteTalk 的比较假设

```text
InfiniteTalk：音频控制、口型基线和长时 streaming 更成熟
H3：参考图细节、画面生成自由度、动作和正式画质可能更高
```

H3 更适合角色高质量近景、情绪反应和需要保持脸部细节的成片。InfiniteTalk 更适合作为长时连续播音参照、H3 口型失败时的对照，以及已有表演视频的重新配音基线。是否能“整体超过”必须用相同粤语音频、相同角色参考和相同输出时长实测，不能由模型定位直接推断。

线上联动的关键边界是 API 是否接受本地 latent。若线上接口只接受图片、视频和音频，则本地 latent 不能直接接续线上采样；可行的联动可能是本地 H3 生成/增强后上传视频或帧，或把线上服务作为 InfiniteTalk/口型兜底，而不是默认存在 latent 级互操作。

## 9. 可靠性判断

目前最可靠的不是某个 H3 工作流，而是以下组合：

```text
固定音频母带
+ 高质量角色参考包
+ 结构化 H3 prompt
+ 短片段生成
+ latent/context 续接
+ FaceRefine
+ 人工验收
```

任何单一插件都不能独立解决身份、口型、身体、镜头和长时连续性。

## 10. 当前部署主线（研究结论，尚待实测）

本轮资料使本地研究方向更明确：第一优先不是寻找“自动拼接器”，而是验证原生 H3 latent/context 链能否把拼接问题变成采样边界问题。

```text
粤语顶级 TTS 母带
→ Source Timeline / source-track lock
→ H3 短片段 + video/audio context
→ 隐藏重叠与 seam probe
→ 3D latent upscale + 正式步数精修
→ 小脸 FaceRefine
→ 最终仍使用外部 TTS 音轨
```

这条链有三个直接含义：

1. B 站案例中每 5 秒跳帧，若只是普通 MP4 首尾拼接，不能代表 H3 原生 MC 的上限；应拆成“模型边界连续性”和“后期拼接失误”两类问题。
2. 外部粤语音频应是最终真值。H3 的 audio latent 用来塑造口型/表演条件，但最终混音不应反复依赖 H3 解码音频。Contex Loop 的 source-track lock 是目前最贴合需求的候选。
3. latent upscale 与 FaceRefine 是互补关系：前者解决全画面时空细节，后者解决远景/小脸的有效像素不足；两者都必须做时间分块、固定 overlap 和身份/接缝检查。

因此，暂时的部署排序是：

```text
H3 原生 MC/Contex Loop（主线）
  + 外部粤语 TTS 锁音
  + 3D latent upscale（画质线）
  + FaceRefine（脸部线）
  + LongMedia/自动编排（流程稳定后再加）
InfiniteTalk（口型与长时保底基线）
云端 API（仅在接受视频/音频/图片级输入时做外围协作，不假定 latent 互通）
```

这仍不是“ H3 已经超过 InfiniteTalk”的结论。真正的判定必须固定同一粤语 TTS、同一参考图、同一输出时长，分别比较 10/30/60 秒的口型、身份、接缝、脸部细节和总耗时。

## 11. 连续口播是唯一主验收场景

本项目的“连贯性”应收紧为：主持人在连续粤语讲话，几乎没有静音转场；每个 chunk 的边界都处于讲话、呼吸、停顿或口型运动中。静音动作片段、音乐视频和只用首尾帧的普通拼接，只能作为辅助资料，不能代表主持人口播效果。

连续口播的边界验收至少要同时观察：

```text
TTS 母带采样时钟
→ 口型是否跨边界继续对应音素
→ 嘴形/牙齿/脸部细节是否突然重置
→ 头部与手势运动是否跳变
→ 身份、发型、服装、光照是否漂移
→ 音频是否出现断裂、重复、音量台阶或音色变化
```

第一批实验应优先选择“连续说话的固定主持人”，而不是先做走向大屏等复杂镜头。每个边界保留前后至少 1 秒视频和音频逐帧检查。H3 MC 只有在真实语音内部边界也能保持连续，才算满足目标。

现有音频和口播稿应先建立时间轴标注：全文时长、自然停顿、句子/语义段落、可接受的 chunk 边界，以及每个边界前后的音素内容。第一轮不要按“每 5 秒机械切段”，而应让分段同时满足 H3 原生帧网格、音频窗口和语义完整性。
